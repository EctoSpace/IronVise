---

> **What this document is - and is not.** ISO/IEC 42001 (like SOC 2) certifies
> **organizations and their management systems, not software products**. No
> tool, IronVise included, can "be ISO 42001 certified" or make you
> compliant by itself. This document is a *control mapping reference*: it maps
> IronVise capabilities to individual ISO 42001 controls so that teams
> pursuing certification can cite the ledger as **supporting evidence** for
> those controls. Certification itself remains an organizational undertaking
> assessed by an accredited body.

## 1. Executive Summary

IronVise is a cryptographically-verifiable, hash-chained event log for autonomous AI agents. This reference maps IronVise's capabilities to the requirements of **ISO/IEC 42001:2023** - the first international standard specifying requirements for an *AI Management System* (AIMS) - indicating where the ledger can supply supporting evidence.

The ledger provides:

- **Tamper-evidence** - SHA-256 hash-chaining and Ed25519 signing make an altered event detectable, not impossible to write; see the README's Honest limitations for what detection assumes.
- **Non-repudiation** - Ed25519 per-session signing keys provide cryptographic proof of authorship.
- **Observability** - Policy-driven observation rules, Prometheus metrics, and SSE event streams give real-time situational awareness.
- **Governance** - Formal logic policies (SOC2, PCI-DSS, OWASP, ISO 42001) are loaded at runtime, version-pinned, and hash-recorded per session.
- **Accountability** - Every agent action, guard decision, and tripwire rejection is appended to the ledger and linked to the original session goal via `goal_hash`.

## 2. Scope

This mapping covers IronVise v0.8.0, which adds:

- `ledger-api` - pluggable `LedgerBackend` trait (Postgres and SQLite implementations)
- Typed refusal records and webhook egress - `GuardDenial` (`guard_denial`) and `TripwireRejection` (`tripwire_rejection`) as both first-class `EventPayload` variants in the hash chain and SIEM webhook egress kinds
- Management GUI - Tauri 2 glassmorphic desktop application
- Python and TypeScript SDKs
- DID support - `session_did` field derived from Ed25519 session key (`did:key:`)

## 2.1 Related mapping - EU AI Act Article 12

[`docs/compliance/eu-ai-act-article12.md`](eu-ai-act-article12.md) maps the same ledger onto
Article 12 (record-keeping) and Article 19 (retention of automatically generated
logs) of the EU AI Act.

The two documents answer different questions and neither substitutes for the
other. ISO/IEC 42001 is a voluntary management-system standard an organisation
chooses to be audited against; the AI Act is binding law with a statutory
application date (2 December 2027 for Annex III high-risk systems, following
Regulation (EU) 2026/1744). Where they overlap - logging, traceability,
accountability - the same `agent_events` chain supplies the evidence.

The stance above holds identically for the AI Act: **the ledger is supporting
evidence, not compliance.** No tool makes a provider conformant with Article 12,
just as none makes an organisation ISO 42001 certified.

## 3. ISO 42001 Clause Mapping

### 3.1 Clause 4 - Context of the Organisation

| Sub-clause | Requirement | IronVise Implementation |
|------------|-------------|-------------------------|
| 4.1 | Understand internal and external context | Session `goal` + `goal_hash` committed at start; any prompt-injection redirect detected by `verify_goal_hash()` |
| 4.2 | Understand needs of interested parties | Policy packs (TOML) express stakeholder requirements enforced at inference time |
| 4.3 | Determine scope of AIMS | Scope defined per-session via `llm_backend`, `llm_model`, `policy_hash` recorded in `agent_sessions` |
| 4.4 | AIMS establishment | The ledger *is* the Management System artefact - all decisions are recorded with cryptographic integrity |

### 3.2 Clause 5 - Leadership

| Sub-clause | Requirement | IronVise Implementation |
|------------|-------------|-------------------------|
| 5.1 | Commitment | `.elc` certificates commit to the event chain via a Merkle root and the ledger tip hash, verifiable offline with `verify-cert`. Individual ledger *events* are Ed25519-signed and checked by `verify-session`; the certificate envelope is signed when exported from a live server that holds the session key (`GET /api/certificates/{id}`) or via `audit`'s saved encrypted session key (`report --format certificate`, `prove-audit`), and is countersigned when an installation issuer key (`ironvise issuer-key init`) is configured. |
| 5.2 | AI Policy | Observation rules, guard LLM, and tripwire patterns implement the AI policy at inference time |
| 5.3 | Roles | `session_did` assigns a W3C Decentralized Identifier to the agent instance, enabling accountability to specific operators |

### 3.3 Clause 6 - Planning

| Sub-clause | Requirement | IronVise Implementation |
|------------|-------------|-------------------------|
| 6.1 | Risks and opportunities | Tripwire (pattern-based) + Guard (LLM-based) form a two-layer risk treatment; rejections logged with reason |
| 6.1.2 | Risk treatment | Red-team module (`red_team.rs`) adversarially probes the agent; findings appended to ledger |
| 6.2 | Objectives | Policy hash pinned to each session; objectives verifiable post-hoc |

### 3.4 Clause 8 - Operation

| Sub-clause | Requirement | IronVise Implementation |
|------------|-------------|-------------------------|
| 8.1 | Operational control | Two-phase commit in `executor.rs`: intent validated before action, result recorded after |
| 8.2 | AI impact assessment | Compliance reports (`/api/reports`, GUI download) summarise session risk posture |
| 8.3 | Lifecycle management | Session lifecycle (`running` → `completed`/`failed`) timestamped in `agent_sessions.finished_at` |
| 8.4 | External AI systems | `llm_backend` + `llm_model` + `policy_hash` recorded per session for full provenance |

### 3.5 Clause 9 - Performance Evaluation

| Sub-clause | Requirement | IronVise Implementation |
|------------|-------------|-------------------------|
| 9.1 | Monitoring | Prometheus endpoint `/api/metrics/security` - guard denials, tripwire rejections, event counts |
| 9.2 | Internal audit | Merkle-root snapshots + chain verification (`verify_chain`) allow independent audits |
| 9.3 | Management review | ISO 42001 compliance report downloadable from Management GUI and REST API |

### 3.6 Clause 10 - Improvement

| Sub-clause | Requirement | IronVise Implementation |
|------------|-------------|-------------------------|
| 10.1 | Continual improvement | Webhook egress (`WEBHOOK_INCLUDE_GUARD`, `WEBHOOK_INCLUDE_TRIPWIRE`) enables SIEM integration and rapid incident response |

## 4. Cryptographic Controls

### 4.1 Hash-Chaining

Every event record contains (canonical v2 scheme, v0.8.0+):
```
content_hash = SHA-256(
    "ELv2\x00" ‖ previous_content_hash ‖ 0x00 ‖ sequence ‖ 0x00 ‖ JSON(payload)
    ‖ 0x00 ‖ session_id ‖ 0x00 ‖ created_at
)
```
Fields are separated by `0x00` delimiters to prevent boundary-manipulation
collisions; the version tag domain-separates the scheme, and `session_id`
(empty for global events) and the microsecond-truncated `created_at` are
always bound into the preimage (see
`crates/core/src/hash.rs::content_hash_input_v2`), preventing cross-session
replay and timestamp tampering. Ledgers written before v0.8.0 verify through
a scheme-fallback path (see `docs/reference/schema.md`). This links events in a
tamper-evident chain with the same structure as other append-only,
hash-linked audit logs (for example Certificate Transparency).

### 4.2 Event Signing

Sessions are assigned a fresh Ed25519 keypair on creation. The public key is recorded in `agent_sessions.session_public_key`. Each event's `content_hash` is signed and stored in `agent_event_signatures`, enabling offline verification:

```bash
ironvise verify-session <UUID>
```
(The `verify-certificate` / `verify-cert` commands instead take a `.elc`
certificate **file path**, not a session UUID.)

### 4.3 Decentralized Identifiers

Every session stores a `session_did` string alongside its signing key, automatically derived as `did:key:` from the session's Ed25519 public key (per the W3C DID Key specification). This provides linkability between sessions and operator identities without a centralised registry.

### 4.4 Merkle Snapshots

When a `.elc` certificate is exported, the system builds a binary Merkle tree over all event content hashes in sequence order (`crates/host/src/certificate.rs`) and stores the resulting root in the certificate. This root allows O(log n) proof that any single event is included, enabling efficient third-party audits without replaying the full history. (Note: `agent_snapshots` stores a `state_hash` over the aggregated snapshot payload - not the Merkle root, which lives in the certificate.)

## 5. Governance Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                     IronVise                       │
│                                                                 │
│  Agent Goal ─► goal_hash ─► Session ─► policy_hash            │
│                                  │                             │
│              Tripwire (layer 1)  │  Guard LLM (layer 2)        │
│                    │             │        │                     │
│              reject/allow        │   DENY/ALLOW                │
│                                  ▼                             │
│              Two-phase Commit ─► Executor ─► Action            │
│                                  │                             │
│              Observation Scan  ◄─┘                             │
│                  flag/abort                                     │
│                    │                                           │
│              Webhook Egress ──► SIEM / PagerDuty / Slack       │
│                                                                 │
│  Hash-chain ● Merkle Snapshot ● Ed25519 Signing ● Cert (.elc) │
└─────────────────────────────────────────────────────────────────┘
```

## 6. Deployment Conformance Checklist

| Control | Env Var / Config | Status |
|---------|-----------------|--------|
| Policy pack loaded | `ECTO_POLICY_PATH` or `--policy` | ✓ Required |
| Webhook configured | `WEBHOOK_URL` | Recommended |
| Guard enabled | `GUARD_LLM_*` | Recommended |
| Tripwire active | `tripwire.json` (`$ECTO_DATA_DIR/tripwire.json`, not an env var) | ✓ Recommended |
| Database persisted | `DATABASE_URL` | ✓ Required |
| Signing keys generated | Automatic per-session | ✓ Automatic |
| Snapshots enabled | `AGENT_SNAPSHOT_INTERVAL` | Recommended |
| DID recorded | Automatic per-session, derived from the session key (not an env var) | ✓ Automatic |
